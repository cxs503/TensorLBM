## 1. Case / method

D2Q9, BGK, float64, single CPU core, lattice units, BGK relaxation time
`nu = (tau − 1/2)/3`. Geometry: plane channel, periodic in `x`, walled in `y`
with single-node solid rows; halfway bounce-back; Guo (2000) second-order
forcing for the pressure gradient (`g = 1e-6`, `nu = 0.05`, `tau = 0.65`).

The in-place A-A step (see the module docstring for the derivation):

1. moments `rho, u` from the current field (three `O(N)` planes);
2. **bounce-back reflections evaluated first**, while every plane is still
   intact, buffered only at the nodes that need them — a compact
   `(index, value)` pair per active direction, i.e. `O(surface)`;
3. rest direction advanced, then planes `1..8` streamed **in place**, each with
   a single `O(N)` copy of that plane; the collision increment is evaluated at
   the *source* node from the precomputed moments and the copied old
   population, so no post-collision array is ever formed;
4. buffered reflections scattered back.

Ordering matters: the reflection for direction `i` needs the *pre-collision*
value of the opposite plane at the same node. Streaming is a permutation within
each plane, so in-place streaming is safe per plane; the cross-plane dependency
is exactly what the buffer removes.

## 2. Results

### 2.1 Equivalence with the fused A-B reference (500 steps each)

| Case | steps | max abs diff | final abs diff | gate 1e-13 |
|---|---|---|---|---|
| periodic | 500 | 8.882e-16 | 8.882e-16 | PASS |
| walled | 500 | 7.772e-16 | 7.216e-16 | PASS |
| moving_wall | 500 | 1.055e-15 | 7.772e-16 | PASS |
| guo_forced | 500 | 1.332e-15 | 1.332e-15 | PASS |

The two kernels are the same scheme; only the storage discipline differs, so the
residual is round-off that grows from the differently associated moment sums
(`f[1]-f[3]+...` vs a weight-tensor contraction). It does not accumulate
systematically: the 500-step maximum stays at the `1e-16` level.

### 2.2 Independent scatter oracle (no shared code)

`tests/test_aa_fused_independent_oracle.py` re-implements the scheme in NumPy as
a **scatter** (`f_i(x+c_i, t+1) <- f_i^post(x,t)`) with explicit per-node,
per-direction loops — the opposite traversal to the pull form used by both
TensorLBM kernels — and its own bounce-back, wall-velocity sampling and Guo
term. 40 steps, walled channel, fluid nodes only:

| Reference | steps | max abs diff on fluid nodes | gate |
|---|---|---|---|
| NumPy scatter vs A-A in-place | 40 | 2.776e-16 | 1e-13 |

Agreement here is evidence about the *scheme* (velocity ordering, shift signs,
wrap, bounce-back target and moving-wall sign), not about a shared helper. The
moving-wall sign in particular is only pinned by this check and by the Couette
profile, never by comparing two pull kernels with each other.

### 2.3 Plane Poiseuille vs analytic (`u_max = gH²/8ν`)

| n (H) | steps | u_max analytic | u_max numeric | u_max rel err | profile L2 rel err | < 3 % ? |
|---|---|---|---|---|---|---|
| 8 | 2500 | 1.600000e-04 | 1.553000e-04 | 2.938 % | 1.883 % | yes |
| 16 | 5000 | 6.400000e-04 | 6.352586e-04 | 0.741 % | 0.476 % | yes |
| 24 | 6000 | 1.440000e-03 | 1.426695e-03 | 0.924 % | 0.774 % | yes |

Worst case over the ladder: **2.938 %** at
`H = 8` — below both the owner 3 % target and the 15 % gate, but
only just, and **the ladder is not monotone**: `H = 24` is worse than `H = 16`.
That is a time-convergence artefact, not a discretisation error — the step
counts are fixed per row while the viscous time `H^2/nu` grows (for `H = 24`,
`H^2/nu = 11520` steps versus the 6000 run here, so the profile is still
relaxing). A convergence-order claim for this kernel is therefore **not** made
here; the numbers above are steady-state *lower* bounds at best for `H = 24`.
The `H = 16` row (5000 steps vs `H^2/nu = 5120`) is the most converged and gives
0.74 % on `u_max`.

### 2.4 Plane Couette (moving wall, halfway bounce-back)

`H = 8`, `u_wall = 0.02`, 2500 steps → max relative profile
error vs the analytic linear profile **2.10e-09** (exactly representable flow; the
residual is round-off and truncation, not a wall-location error).

### 2.5 Mass conservation, closed walled box

16×16 box, all four walls solid, 500 steps, perturbed rest state:
max relative mass drift **3.07e-14**, final **3.07e-14** (gate 1e-12).
Bounce-back written inside the pull pass conserves mass to round-off; a
bounce-back written on solid nodes does not (§R1 history of the superseded
kernel).

## 4. Storage: the A-A property, measured

`measure_storage.py` runs each kernel in a fresh subprocess on a 900×900 D2Q9
float64 field (58.32 MB per field) and reads `VmHWM` (kernel-provided peak
resident set) before and after three steps:

| Kernel | peak above the carried field | equivalent in fields |
|---|---|---|
| fused A-B (`aa_fused_push_pull`) | 126.9 MB | **2.17** |
| fused A-A in place (`aa_fused_push_pull_inplace`) | 14.6 MB | **0.25** |

`VmHWM` is a high-water mark, so allocator caching can only *over*-estimate what
the kernel touches: the A-B number is dominated by the second field plus the
intermediate `9N` collision/equilibrium temporaries, the A-A number by the four
`O(N)` planes plus the per-plane copy. Repeated runs of the same script give
2.17–2.86 / 0.25–0.45 fields depending on allocator state; the ratio is ~9×.

The structural claim is additionally asserted as a test rather than a
measurement: `test_no_second_field_is_allocated` intercepts `torch.empty*` and
fails if a `Q x N` tensor is allocated during the A-A step, with the A-B kernel
as the positive control that proves the probe bites
(`second_field_allocations = {'aa': 0, 'ab': 1}`).

**What is *not* claimed**: on this workload the A-A kernel is *not* faster —
Python/torch op launch dominates (~10.0 ms/step for a 4×H lattice, both kernels), so
the memory saving is a structural property, not a speed-up. The paper-level
benefit needs a compiled kernel; that remains separate work.

## 5. Notes, limitations, pitfalls

1. **Cross-plane bounce-back dependency.** The naive in-place loop is wrong
   whenever the opposite plane has already been overwritten; the reflections
   must be evaluated before the streaming loop (or the loop split into parity
   halves). Any in-place implementation that streams first and then applies
   bounce-back will silently lose mass at walls.
2. **D2Q9, BGK, float64, CPU.** No MRT/regularised collision, no 3-D, no
   non-periodic inlet/outlet. The pull/shift form is periodic in both
   directions; `x`-periodicity is real physics here (fully developed channel),
   `y` is masked by walls.
3. **Staircase walls only** (single-node halfway bounce-back); no interpolated
   curved-wall bounce-back, no Zou–He velocity inlet.
4. **The in-place step mutates its argument.** Callers must not hold references
   they expect to be unchanged — this is the one API difference from
   `fused_push_pull_step`, and it is asserted by `test_in_place_contract`.
5. The storage numbers are resident-set measurements on a shared node, not an
   allocator API; they are reported with run-to-run variation rather than as a
   single exact figure.
6. Float32 is untested; no bit-identity claim is made there.

```bash
cd TensorLBM
PYTHONPATH=src pytest tests/test_aa_fused_inplace.py -q              # 11 tests, ~85 s
PYTHONPATH=src pytest tests/test_aa_fused_independent_oracle.py -q   # 6 tests, ~5 s

    --out benchmarks/verified/fused_push_pull_aa_pattern/storage_aa.json
PYTHONPATH=src python benchmarks/verified/fused_push_pull_aa_pattern/run_aa_inplace.py
PYTHONPATH=src python benchmarks/verified/fused_push_pull_aa_pattern/make_figs_aa_inplace.py

```

`run_aa_inplace.py` is the long pole (≈6 min single core for the full ladder).
It was submitted to the cluster queue as `cj2728`, which was still queued after
10 minutes and was killed unconsumed; the same script was then run locally in
`--part` chunks (`equiv`, `poiseuille --n 8|16|24`, `couette`, `mass`), each
under the local 2-minute guard, writing into the single result file. No number
in this document comes from a cluster run.
