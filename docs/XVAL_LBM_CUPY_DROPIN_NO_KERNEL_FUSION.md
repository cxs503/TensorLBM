## ① Case introduction: physics, geometry, parameters

The OSS project `ebinan92/Fingering_dynamics` simulates non-Newtonian viscous fingering with a **Swift–Osborn–Yeomans (SOY) free-energy D2Q9 lattice Boltzmann model** (two populations `f` (momentum) and `g` (order parameter `psi`), chemical potential `mu = a psi(1-psi^2) - kappa lap(psi)`, Guo forcing of the capillary force `mu grad psi`). Its GPU strategy is the **“cupy drop-in, no kernel fusion”** practice: `lattice_boltzmann/fingering_periodic_gpu.py` is the NumPy script with `import numpy as np` replaced by `import cupy as cp` — no custom CUDA kernels, no fused push/pull.

The cross-validation question is therefore: **does the array-API drop-in practice transfer to TensorLBM's PyTorch stack, i.e. does one implementation driven through two array namespaces reproduce the OSS numbers and the analytic physics?**

Benchmark case: a **static droplet** of radius `R` in a periodic box. The equilibrium condition is the Young–Laplace law `dp = sigma/R`, measured as the mean pressure difference between the droplet interior (`r < R - xi`) and exterior (`r > R + xi`), with the OSS pressure definition `p = rho/3 + psi mu`.

The predeclared expectation was “error shrinks as R/xi grows (curvature correction O(xi/R))”. The measured trend is the **opposite sign**: |error| grows slightly with R (−0.25 % at R=10 to −0.60 % at R=20). The magnitude stays ~1 % at every radius, so the data do **not** support a clean convergence order; the residual is dominated by the sampling-time transient rather than by a curvature term. Recorded as a falsified sub-hypothesis, not quietly dropped.

**Pitfall (measured, not asserted):** initialising the interface twice as steep (`tanh(2(r-R)/xi)` instead of the equilibrium `tanh((r-R)/xi)`) leaves the run at **+54.61 %** after the same 2000 steps — outside the 15 % band. The scheme relaxes the initial width very slowly, so an initial condition that is not the SOY equilibrium profile masquerades as a physics error. This is exactly the failure mode of the previous round's first attempt.

### ⑤.3 Other pitfalls found while doing this

1. **“Identical to OSS” was overstated in round 0.** The OSS pressure is `p = rho/3 + psi mu` (`getP`), not `rho/3 + psi mu/3`. Both forms are now implemented and measured (they differ by a few tenths of a percent here, not “identical”).
2. **The OSS reference blows up if executed naively on a periodic droplet.** OSS hard-codes ghost columns for its Zou–He inlet/outlet (`left_wall = +1`, `right_wall = -1`); with a droplet box those ghosts create a spurious interface and the run diverges (NaN within ~400 steps). The adapter resets them to the far-field value −1 — documented rather than hidden, and the residual OSS-vs-port difference is 0.0174 %.
3. **Single-sample reporting hides the transient.** The previous round quoted the 0.07 % sample while the same run oscillated between −7 % and +1 % over the preceding 400 steps. The band is now part of the artefact (`dp_history.csv`).
4. **Torch eager is ~3.5x slower per step than NumPy on this CPU host** (17.53 ms vs 5.08 ms), at identical op counts — the direct cost of “no kernel fusion”. A GPU device swap changes the constant, not the structure; fusion would need the custom kernels the OSS project deliberately avoided.
5. **Worktree trap**: this host has an editable `tensorlbm` install pointing at another checkout, so `import tensorlbm` silently loads foreign code. The test module purges and re-imports from this worktree's `src/` explicitly.
