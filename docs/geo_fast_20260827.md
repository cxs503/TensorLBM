## 1. Where the milliseconds went (profile first)

Standalone reproduction of the cache-miss front-end
(`suboff_component_counts` + bookkeeping, the exact functions the echo
router calls on a miss) over a 20-move slider sweep on the production
grid 64 x 64 x 128, p50 per move (`profile.json`):

| stage                       | CPU before | CUDA before | CPU after | CUDA after |
| --------------------------- | ---------: | ----------: | --------: | ---------: |
| meshgrid                    |    0.017 ms |    0.038 ms |  0.016 ms |   0.035 ms |
| hull mask (incl. profile)   |    7.282 ms |    6.397 ms |  0.295 ms |   0.357 ms |
| sail predicate              |    4.901 ms |    1.066 ms |  5.816 ms |   1.025 ms |
| fin predicate               |    2.540 ms |    0.582 ms |  2.896 ms |   0.577 ms |
| reductions (6x `.item()`)   |    0.318 ms |    0.198 ms |  0.347 ms |   0.191 ms |
| **total miss**              |   **16.548 ms** | **8.823 ms** | **10.162 ms** | **2.286 ms** |

Attribution of the two dominant costs:

- **numpy radius-profile round trip inside `suboff_hull_mask` — 5.7 ms.**
  The hull-form code maps the full `(nz, ny, nx)` float32 tensor to numpy
  (float64), evaluates `suboff_radius_profile` elementwise over 524 288
  cells (the bow segment alone runs `np.power(a1, 1/2.1)` over ~120 k
  cells), and copies back. But `xi` depends only on the axial index: the
  profile has exactly `nx = 128` distinct inputs. Evaluating the row costs
  **0.054 ms** — 105x less — and returns bit-identical values.
- **full-volume CAD predicates on CPU — 7.4 ms.** The sail and fin point
  predicates are ~70 elementwise ops over the whole volume each; on CPU
  they cost 4.9 + 2.5 ms, on CUDA 1.1 + 0.6 ms.

(The `trt_f16` server showed the same CPU work as 44.9 ms — the f16
engine host threads contend with the geometry stage; moving the stage to
the GPU also removes that failure mode.)

## 2. What changed

Additive, default-on for CUDA-visible services, every output bit-identical:

1. `suboff_hull_mask` (`src/tensorlbm/suboff_cad.py`) evaluates the axial
   coordinate on the `(nx,)` row and the radial distance as a
   `(nz, ny, 1)` broadcast view instead of a full meshgrid. Elementwise
   ops see exactly the values the full grid produced, so the mask is
   bit-identical while the numpy profile round trip shrinks `ny*nz`-fold.
   This also speeds up the no-corpus `build_mask` path (16.6 -> 12.1 ms
   CPU, 10.5 -> 4.2 ms CUDA standalone).
2. `GeometryEchoPipeline` (`src/tensorlbm/ai/geometry_pipeline.py`) gains
   `counts_device` (default `None` = auto): the echo device when it is
   CUDA, else any CUDA device visible to the process, else CPU. The
   integer decomposition (voxel counts, projected areas — reductions of
   the same elementwise predicates) is device-invariant, so the served
   condition channels stay bit-exact; this is why auto is allowed to use
   a visible GPU even when the torch front-end device is CPU (the TRT
   echo configs are exactly that case). Explicit `"cpu"` / `"cuda"` /
   torch device strings force a side.
3. Router (`app/backend/routers/drag_echo.py`): `TENSORLBM_DRAG_ECHO_COUNTS_DEVICE`
   env override (`auto` default) wired through `build_default_echo_service`,
   and `/api/drag/echo/health` now reports `counts_device`.

**Not shipped:** param-keyed incremental mask reuse (re-voxelising only
the axis that moved). It cannot be made bitwise-identical in general —
appendage predicates interact with the hull surface they intersect — and
the full on-device rebuild already meets the budget, so the risky route
was dropped per the brief.

Rollback: `TENSORLBM_DRAG_ECHO_COUNTS_DEVICE=cpu` restores the CPU
decomposition (plus the section-1 row optimisation, which is bitwise and
stays).
