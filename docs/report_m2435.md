## 1. 案例介绍（Case Introduction）

### 1.1 物理背景

船舶总体性能平台（ship-performance-platform）是 外协方船舶总体性能学科的核心计算平台，覆盖以下九个学科方向：

- **阻力**（Resistance）：船体阻力预报与实验对标
- **推进**（Propulsion）：推进器性能与船-桨匹配
- **耐波**（Seakeeping）：波浪中船舶运动响应
- **操纵**（Maneuvering）：船舶操纵性预报
- **稳性**（Stability）：静稳性与动稳性评估
- **结构**（Structure）：船体结构强度分析
- **振动噪声**（Vibration & Noise）：振动与噪声预报
- **绿色航行**（Green Navigation）：能效与排放优化
- **冰区航行**（Ice Navigation）：冰载荷与冰区性能

### 1.2 问题陈述

平台在快速迭代过程中积累了**验证欠账**（verification debt）：部分能力声明缺乏充分的验证证据，或验证流程不完整。这导致：

- 能力台账（capability ledger）的可信度下降
- S3 判级（证据等级：REAL/MOCK/STUB/WITHHELD/NOT_SUPPORTED）缺乏一致性
- 新能力交付时无法快速判断是否满足精度标准（对标实验/参考值误差 >15% 不可接受）

### 1.3 任务目标

Mission 2435 的目标是清偿验证欠账，具体包括：

1. **扫描提案池**：只读扫描 `/root/tp-agent/proposals/` 中的待办提案
2. **审查已有报告**：通过 `GET /api/v1/tensor/reports?limit=20` 提取报告的「局限/待办」节
3. **检查 guide_tracker 缺口**：识别验证指南（guide_tracker）中的缺失项
4. **补全验证证据**：为缺失验证的能力补充测试、对标数据、误差分析
5. **更新能力台账**：将验证结果落盘到能力台账，更新证据等级

## 2. 方法论（Methodology）

### 2.1 工作流程

```
1. 提案池扫描 → 识别待验证能力
2. 报告审查 → 提取「局限/待办」清单
3. guide_tracker 缺口分析 → 确定验证优先级
4. 验证执行 → 运行测试、对标实验/参考值
5. 误差判定 → 关键量 vs 基准误差逐项列出
6. 能力台账更新 → 落盘验证证据
7. 报告发布 → POST /tensor/reports（失败）
```

### 2.2 验证标准

- **精度标准**：对标实验/参考值误差 >15% 不可接受
- **几何验证**：必须先验证 Cb/L/B（方形系数/船长/船宽）
- **证据分级**：
  - REAL：真实算法，有充分验证
  - MOCK：硬编码/随机，无物理意义
  - STUB：空壳，未实现
  - WITHHELD：证据不足，无法判定
  - NOT_SUPPORTED：不支持

### 2.3 工具链

- **计算平台**：船舶总体性能平台 API（:8001）
- **报告系统**：Tensor API（:8010）
- **版本控制**：Git（commit 81f009e）
- **测试框架**：pytest（推测，未留档）

## 7. 改进建议（Recommendations）

### 7.1 工件管理

1. **强制工件保留**：所有验证任务必须在 worktree 内保留工件
   - `docs/`：文档、报告、误差分析
   - `artifacts/`：原始数据、处理脚本
   - `runs/`：运行日志、测试结果

2. **工件清单**：任务完成前必须生成工件清单（manifest），列出所有保留的文件

3. **工件审计**：守望线应自动检查工件完整性，缺失则派补报单

### 7.2 报告发布

1. **预检机制**：POST 前先用 dry-run 模式验证请求体格式
2. **错误诊断**：422 错误应触发根因分析，而非直接标记失败
3. **重试策略**：网络/临时错误应自动重试，格式错误应提示修正

### 7.3 验证流程

1. **验证清单**：任务开始前明确验证清单（哪些能力、哪些关键量、哪些基准）
2. **误差门限**：明确误差门限（如 <3%），未达标则标记 FAIL
3. **独立审查**：关键验证应邀请独立审查（adversarial-review）
