Two root causes survived the earlier round of this clearance (the device-family recording in
`suboff_wallfn_fullgrid_runner`, the `pytest.approx(0-d tensor)` misuse in

## 1. `CutCellBGK2D.Q` used an illegal boolean-index form

```python
field[:, mask] = (density[self.group_map[mask]] * self.volume_m3[mask, None]).T
```

`volume_m3` is the **cell** cut volume, shape `(ny, nx)`. A 2-D boolean mask followed by a
trailing `None` binds the new axis *between* the two masked dimensions, so torch compared a
`[ny, nx]` mask against a `[ny, 1, nx]` tensor:

```
IndexError: The shape of the mask [10, 12] at index 1 does not match the shape of
the indexed tensor [10, 1, 12] at index 1
```

Every consumer of `Q` — the state snapshot, the checkpoint ledger, the restart path — therefore
died at construction, which is why 13 of the 19 pre-existing tests in
`tests/test_cut_cell_bgk_2d.py` never reached their assertion.

Fix (index the fluid cells first, then add the population axis):

```python
cell_volume = self.volume_m3[mask]
field[:, mask] = (density[self.group_map[mask]] * cell_volume[:, None]).T
```

The cut-cell case under test has 116 fluid cells merged into 114 groups, so the expansion is
not a simple gather: groups that span several cells must be weighted by each cell's own open
volume. Measured on that case (`summary.json → cut_cell_probe`):

| quantity | value |
|---|---|
| field shape returned by `Q` | `(9, 10, 12)` |
| fluid cells / merged groups | 116 / 114 |
| max per-cell residual \|`Q.sum(0) - rho_group·V_cut`\| | `8.9e-16 kg/m` |
| mean per-cell residual | `1.3e-16 kg/m` |
| total mass through `Q` vs `group_Q` | 223.265116489676840 vs 223.265116489676840 kg (rel. err `0.0`) |

i.e. the reconstruction is exact to float64 round-off; before the fix it did not exist at all.

## 2. `multi_gpu.auto_decompose` silently degraded to one CPU domain on an SDAA node

`auto_decompose` probed CUDA only:

```python
n_gpus = torch.cuda.device_count() if torch.cuda.is_available() else 0
devices = ["cpu"] if n_gpus == 0 else [f"cuda:{i}" for i in range(n_gpus)]
```

On the SDAA runner (`cuda.is_available() == False`, `torch.sdaa.device_count() == 1`) this
returned `["cpu"]`, so a 1-card SDAA host was described as a single-CPU domain and the whole
slab decomposition collapsed to an in-process CPU run. The module's own TDD contract
(`tests/test_multi_device_sdaa_common.py`) already asked for an explicit family request, which
the implementation never grew; three of those tests sat in `tests/ci_quarantine.txt`.

Fix: a `DEVICE_FAMILIES = ("cuda", "sdaa", "cpu")` vocabulary, an `_accelerator_family()` probe
(CUDA first, then SDAA, then CPU), and keyword-only `device_type=` / `n_devices=` overrides on
`auto_decompose` (`n_gpus` is kept as the legacy alias). An explicit `device_type` is honoured
as-is — it describes the intended layout even on a host that lacks the backend — while the
auto-detected path only ever returns cards torch reports.

| call | before | after |
|---|---|---|
| `auto_decompose(f)` | `['cpu']` | `['sdaa:0']` |
| `auto_decompose(f, device_type="sdaa", n_devices=2)` | `TypeError` | `['sdaa:0', 'sdaa:1']` |
| `auto_decompose(f, device_type="cpu", n_devices=0)` | `TypeError` | `['cpu']` |

## Remaining debt (deliberately out of scope)

* `DomainDecomposition.from_devices()` still hard-codes `"cuda:{i}"`; the
  `test_from_devices_sdaa` / `test_from_devices_cpu` quarantine entries therefore stay. Fixing
  them means changing a public constructor signature, which belongs to the multi-card feature
  PR, not to a red-clearance patch.
* The multi-card equivalence entries (`test_multi_card_*_matches_monolithic`) need ≥2 real
  devices; this host exposes one SDAA card, so they cannot be validated here.
* `tests/ci_quarantine.txt` still contains 3 duplicate lines from batch 3 (the two
  `test_mlups_wall_function` parametrisations listed twice) — harmless for the xfail hook,
  cleaned up with the performance-lane follow-up.
