# TRT backend for the drag echo service — 2026-08-27

Branch `exp/trt-echo` (base `main` = `ce7ab98b8`).  Lets the served echo
stack (PR #241 `DragSurrogateService` + `GeometryEchoPipeline` +
`app/backend/routers/drag_echo.py`) run its ensemble inference on the
TensorRT engines of PR #249 instead of torch eager, selected by an
environment variable, with the default serving path **bit-identical** to
before.  Headline (warm, real HTTP, GPU 2): `POST /api/drag/echo/params`
B=1 p50 **8.19 ms (torch-GPU) -> 1.99 ms (TRT fp32-strict) / 2.15 ms
(TRT f16)**; the inference segment alone drops 7.16 ms -> 0.94 ms (7.6x).
Verdicts (flag + reasons) identical on all 24 design x backend rows.
Full tables below and in `/nfs/wangxi/runs/trt_echo_20260827/`
(bench.jsonl / summary.json / report.md).

## What was added

| file | role |
|---|---|
| `src/tensorlbm/ai/service_backends.py` | `make_backend(kind, ...)` factory (`torch` / `onnx` / `trt`), `resolve_backend_kind`, the service-protocol adapter `FusedGraphBackend`, degrade-to-torch fallback with recorded reason |
| `src/tensorlbm/ai/inference_service.py` | **only change to an existing file**: `DragSurrogateService.from_checkpoints` gains `backend_kind` / `backend_plan` (+13 lines incl. docstring); non-default kinds delegate to `make_backend` |
| `tests/test_service_backends.py` | factory + protocol tests; ONNX and TRT tiers `skipif`-gated; real-plan parity + three-backend verdict-consistency class (server-gated) |
| `docs/trt_echo_20260827.md` | this document |

Why a new `service_backends.py` rather than extending `trt_deploy.py`:
the factory must treat torch, ONNX and TRT uniformly and import
`inference_service` (torch) for the protocol base class, while
`trt_deploy.py` is deliberately torch-free (it runs in the deploy venv
without torch).  Mixing the two would break that venv's import graph.

## The service protocol (what a backend must satisfy)

Unchanged from #241 — `ModelEnsembleBackend`'s surface:

- `predict(fields (5, ny, nx), cond (N, 8)) -> (M, N)` float64 member
  matrix of **linear C_D**, raw un-normalised inputs;
- `predict_batch(fields (G, 5, ny, nx), cond (N, 8) concatenated,
  counts (G,)) -> (M, sum counts)`;
- `kind` / `n_members` / `member_labels()` for result provenance.

`mean` / `std` / `lo` / `hi` are NOT backend outputs: the service derives
them on the host from the member matrix (`ensemble_stats`, float64),
identically for every backend — so UQ fields cannot drift between
backends.  The TRT graph's in-graph float32 statistics
(`cd_mean`/`cd_std`/`cd_min`/`cd_max`) are deliberately unused on the
serving path (float32 accumulation ≠ float64 host reduction); they remain
reachable via `FusedGraphBackend.runtime.predict_stats` for probes.
Nothing in the protocol is `None` for TRT: the engines expose the full
per-member matrix.

`FusedGraphBackend` subclasses `ModelEnsembleBackend` **without building
torch models**: this is what makes the existing `isinstance` dispatch in
`DragSurrogateService.predict` / `GeometryEchoPipeline._run_backend` /
`predict_from_stl` route it down the model path — no dispatch code had to
change.  The fused artifacts fold per-member normalisation into the graph,
so the raw-input contract already matches.

Chunking: the PR #249 engines have a bounded dynamic condition batch
(profile `cond` 1..8).  The adapter slices cond rows into `<= chunk`-row
runtime calls (chunk = `min(trt_max_batch, engine profile max)`) and
concatenates along the row axis, in order.  A row's value can in principle
depend on its chunk shape at float32 LSB level (TRT picks tactics per
input shape); measured on the real plans, the same row in a batch of 4 vs
a batch of 8 came out **bitwise identical** (pinned by
`tests/test_service_backends.py::TestRealPlans`), and the end-to-end
parity floors below confirm it does not matter at serving shapes.

## Backend selection (service-construction layer, no app/ changes)

`DragSurrogateService.from_checkpoints(..., backend_kind=None,
backend_plan=None)`:

1. explicit `backend_kind` argument wins;
2. else `TENSORLBM_DRAG_BACKEND` (`torch` / `onnx` / `trt`);
3. else `torch` — and with the argument unset AND the env unset, the
   backend is built by the original `ModelEnsembleBackend(ckpts, device=...)`
   line, so the default serving path is byte-for-byte the pre-TRT code.

Environment variables (all default unset = old behaviour):

| var | meaning |
|---|---|
| `TENSORLBM_DRAG_BACKEND` | `torch` (default) / `onnx` / `trt` |
| `TENSORLBM_DRAG_BACKEND_PLAN` | `.plan` (trt) or `.onnx` (onnx) artifact path |
| `TENSORLBM_DRAG_BACKEND_PRECISION` | honest label suffix only, e.g. `fp32_strict`, `f16` — the artifact decides the math; serves `EchoResult.backend` / `/health` |
| `TENSORLBM_DRAG_BACKEND_FALLBACK` | `torch` = degrade (with the failure reason recorded on `backend.init_report`) instead of refusing to start |

Invalid values fail loudly at construction (no silent degradation).  The
echo router (`app/backend/routers/drag_echo.py`) was NOT touched: it
reaches the hook through `build_default_service` ->
`from_checkpoints`, so the running service selects TRT purely by
environment.  This keeps zero file overlap with the parallel
`exp/demo-mount` branch.

Deploy recipe (deploy venv has tensorrt + cuda-python but no torch; torch
+ fastapi are borrowed from the tensorlbm venv — no packages installed):

```bash
CUDA_VISIBLE_DEVICES=2 \
PYTHONPATH=<repo>/src:/nfs/wangxi/venvs/tensorlbm/lib/python3.12/site-packages \
LD_LIBRARY_PATH=/nfs/wangxi/venvs/tensorlbm/lib/python3.12/site-packages/nvidia/cudnn/lib \
TENSORLBM_DRAG_CKPT_DIR=/nfs/wangxi/runs/b4_serve_20260824/ckpts \
TENSORLBM_DRAG_RUN_DIR=/nfs/wangxi/runs/b4_v4_20260824 \
TENSORLBM_DRAG_BACKEND=trt \
TENSORLBM_DRAG_BACKEND_PLAN=/nfs/wangxi/runs/deploy_latency_20260825/ensemble_cfull_stacked_trt_fp32.plan \
TENSORLBM_DRAG_BACKEND_PRECISION=fp32_strict \
    /nfs/wangxi/venvs/deploy/bin/python -m uvicorn ...   # backend= "trt_fp32_strict" in /health
```

## Measured end-to-end (this slice, GPU 2, RTX 5090)

Setup: real HTTP against a uvicorn process mounting the repo's
`drag_echo` router (minimal `echo_server.py`, runs dir), backend selected
only via the env hook above; corpus `b4_v4_20260824` (274 fields);
checkpoints `b4_serve_20260824` (5 members, labels m0..m4); PR #249 plans.
Warmup 30 calls, then >= 5 s steady state (>= 100 calls) per row; client
wall time over a keep-alive connection; `server_stages_ms` from the
pipeline's own `info.timings_ms`.  Raw events: `bench.jsonl`.

Reading: TRT accelerates **only the inference segment** — 7.6x (fp32

validation + response shaping remains.  Geometry moves are bounded by the
CPU mask front (14–48 ms observed), so slider drag stays ~20 ms under any
backend.

### Verdict consistency + C_D differences

6-design batch x 4 configs (24 rows): **flag and reasons identical on
every row** (`reject` mother_full — its Re grid lower edge 40 sits below
the served envelope [1.639, 2.963] in log10, an intentional scenario
artifact; `review` hullform_lod_1.15 — corpus honesty downgrade; `ok`
otherwise).  Guard scores agree to 6 decimals across all backends
(the guard is CPU-only and exact).  Max relative linear C_D vs the
torch_cpu row:

| config | mother_full (B=8) | sail_0.8 | sail_1.25 | fin_0.7 | hullform_lod_1.15 | sail_2.5 |
|---|---|---|---|---|---|---|
| torch_gpu | 1.13e-4 | 3.9e-7 | 5.9e-7 | 8.3e-7 | 1.6e-7 | 6.0e-7 |
| trt_fp32_strict | **2.6e-7** | 1.2e-7 | 1.6e-8 | 1.4e-7 | 3.2e-8 | 7.1e-8 |
| trt_f16 | 1.79e-3 | 2.6e-4 | 7.3e-5 | 9.3e-5 | 2.5e-4 | 2.0e-4 |

choice (#249 finding 4), pre-existing and unrelated to TRT.

## Honest deviations / notes

1. **Default path invariance**: with `backend_kind=None` and
   `TENSORLBM_DRAG_BACKEND` unset, `from_checkpoints` still constructs
   plain `ModelEnsembleBackend` (pinned by
   `test_from_checkpoints_default_builds_plain_model_backend`).
2. **Plans are not portable** (#249): sm_120 / TRT 11.2.1.2-cu12 engines,
   profile cond 1..8; rebuild from the ONNX siblings elsewhere.
3. **TF32**: the tf32 plan is NOT wired into any recommended config; the
   shipped fp32 plan is the strict build (`clear_flag(TF32)`), parity
   ~1.6e-7 max |log10 C_D| vs torch-CPU (re-measured this slice: 1.56e-7
   at 9 rows incl. the 8+1 chunk boundary).
4. **f16 plan**: ~7.7e-4 max |log10 C_D| (~0.18 % linear C_D) —
   slider-echo class only, exactly as #249 recorded.
5. The benchmark mounts the repo router on a minimal FastAPI app rather
   than the full platform `main.py` (which pulls ~25 unrelated routers,
   job manager and middleware); the measured path is the echo route stack
   itself over real HTTP.  Full-app overhead would add the same constant
   to every backend.
6. torch-GPU eager deviates from its own CPU reference at B >= 2
   (~1.3e-4 log10, cuDNN batch-dependent algorithm choice — #249 finding
   4); the verdict-consistency table therefore uses torch_gpu as its
   reference for flags (guard is CPU-only, exact) and reports C_D diffs
   against both torch rows.
7. GPU clocks could not be locked (no privileges): `nvidia-smi -lgc`
   denied; variance is covered by >= 100-sample p50/p90.
